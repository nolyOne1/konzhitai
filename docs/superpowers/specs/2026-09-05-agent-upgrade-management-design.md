# 云令代理版本与分批升级管理设计

日期：2026-09-05
状态：已确认

## 1. 背景

云令已经能够接入 Linux 执行服务器，代理会持续上报版本、资源与运行状态；控制平面也能提供当前代理安装包和不可变下载地址。但现有能力只覆盖首次安装：管理员可以看到单台服务器的代理版本，却不能统一盘点版本、下发升级、查看进度或回滚。

随着执行服务器增加，继续逐台登录服务器更新代理会产生重复操作，也无法在升级期间自动处理正在运行的任务。本阶段补齐代理版本仓库、升级计划、分批推进、失败暂停和节点回滚，使后续新增腾讯云、京东云或其他云服务器后都能从同一控制台完成代理维护。

## 2. 已确认的产品决策

- 升级由管理员在控制台手动创建，不在首版启用无人值守自动升级。
- 管理员选择目标版本和目标服务器，系统按批次执行。
- 首批固定为 1 台服务器；首批验证成功后自动推进后续批次。
- 后续批次大小可在创建计划时设置，默认仍为 1 台。
- 升级前服务器自动进入排空状态，不再接收新任务。
- 已在运行的任务不会被强制终止；系统等待任务自然结束后再升级。
- 任一节点失败会立即暂停整个升级计划。
- 失败批次自动回滚；此前已经成功的批次保持目标版本，等待管理员决定继续或单独回滚。
- 首版同一时间只允许运行一个升级计划。
- 管理端页面、运行状态、错误提示和操作记录全部使用中文。

## 3. 目标与非目标

### 3.1 目标

- 在控制台统一查看所有服务器的代理版本与升级状态。
- 保存多个不可变代理版本，并允许选择任一可用版本升级或回滚。
- 不依赖控制台保存 SSH 密码或管理员逐台登录服务器。
- 升级过程与任务调度联动，保证运行中的任务不被升级流程中断。
- 控制面或代理重启后能够从持久化状态继续处理或对账。
- 每台服务器均保留清晰的阶段、时间、结果和中文错误摘要。

### 3.2 非目标

- Windows、macOS、非 systemd Linux 和 32 位架构。
- 按时间自动升级、自动选择维护窗口或无人审批的全自动升级策略。
- 在浏览器内编译代理程序或直接上传任意可执行文件。
- 同时运行多个相互重叠的升级计划。
- 通过 SSH、云厂商命令执行接口或远程桌面替换代理。
- 自动回滚此前已经验证成功的批次。

## 4. 总体架构

本功能由五部分组成：

1. **多版本代理仓库**：保存版本清单及 Linux amd64、arm64 的不可变安装包。
2. **升级计划服务**：创建计划、选择批次、推进状态、暂停、继续和取消未开始节点。
3. **代理升级协议**：在现有 WebSocket 长连接上增加升级指令、阶段回报和结果回报。
4. **节点本地升级器**：由 systemd 以 root 身份执行原子替换、重启和本机回滚。
5. **中文控制台**：提供版本盘点、计划创建、实时进度和历史记录。

控制面只负责选择版本、编排状态和判断结果。安装包下载、校验、暂存和本机替换均在目标服务器执行。升级使用现有代理连接，因此新服务器只要完成一次注册，后续不需要再配置 SSH 凭据。

## 5. 多版本代理仓库

### 5.1 发布内容

每个可用版本包含：

- 唯一版本号；
- Linux amd64 安装包；
- Linux arm64 安装包；
- 每个安装包的文件名、字节数和 SHA-256；
- 发布时间、发布说明和是否为当前推荐版本。
- 版本能力集合；包含本地升级器的版本声明 `self_upgrade_v1`。

版本号及安装包内容一经发布不得覆盖。撤回版本只会阻止创建新的升级计划，不删除已经被计划或回滚记录引用的文件。

### 5.2 存储方式

代理产物使用不可变对象路径：

```text
agent-releases/{version}/{sha256}/{fileName}
```

数据库只保存可信元数据和对象引用，安装包仍通过控制平面的同源下载接口提供。旧的 `GET /api/releases/agent/latest` 保持兼容，但其内容改为从推荐版本生成；新增历史版本查询接口供控制台和代理升级使用。

### 5.3 发布入口

新版本通过独立的运维命令导入：命令先校验两个架构、固定文件集合、包内 `agent-version`、字节数和 SHA-256，再写入对象存储与数据库。构建流水线以同一版本参数构建两个架构，在可执行的本机架构上校验二进制自报版本，并在 arm64 真实节点验收时再次核对自报版本；导入命令不要求 amd64 主机直接执行 arm64 二进制。浏览器首版不提供二进制上传入口。

导入成功后，管理员可以将版本设为“推荐版本”。新服务器接入向导继续默认安装推荐版本；已有服务器不会因为推荐版本变化而自动升级。

首次启用多版本仓库时，如果数据库中尚无代理版本，API 会从现有只读 `YUNLING_AGENT_RELEASE_DIR` 导入当前清单和两个安装包，并把它设为推荐版本。旧安装包允许没有 `agent-version` 和升级单元，此时版本能力为空，只能继续用于原有接入和历史下载，不能作为自动升级目标。该步骤幂等：仓库已有任一版本时不再自动导入；导入失败时代理发布与升级接口返回暂不可用，但其他控制台功能继续运行。

## 6. 数据模型

### 6.1 `agent_releases`

- `id`
- `version`，唯一
- `status`：`available`、`withdrawn`
- `recommended`
- `release_notes`
- `manifest_sha256`
- `capabilities`
- `created_at`
- `created_by`

### 6.2 `agent_release_artifacts`

- `id`
- `release_id`
- `os`
- `arch`
- `file_name`
- `byte_size`
- `sha256`
- `object_key`

同一版本必须同时具有唯一的 `linux/amd64` 和 `linux/arm64` 记录。

### 6.3 `agent_upgrade_plans`

- `id`
- `target_release_id`
- `status`：`pending`、`running`、`paused`、`succeeded`、`cancelled`
- `first_batch_size`，首版固定为 1
- `batch_size`
- `drain_timeout_seconds`
- `reconnect_timeout_seconds`
- `verification_seconds`
- `current_batch`
- `created_by`
- `created_at`、`started_at`、`finished_at`
- `pause_reason`

### 6.4 `agent_upgrade_targets`

- `id`
- `plan_id`
- `server_id`
- `batch_number`
- `source_version`
- `source_draining`，记录升级前是否已经人工排空
- `target_version`
- `status`
- `attempts`
- `command_id`
- `error_code`、`error_message`
- `started_at`、`updated_at`、`finished_at`

目标状态为：

```text
waiting → draining → downloading → verifying → installing
        → reconnecting → health_checking → succeeded
```

失败路径为：

```text
任一执行状态 → rolling_back → rolled_back
                         └→ manual_intervention
```

未开始目标可以进入 `cancelled`。所有状态变化追加写入升级事件记录，供控制台展示时间线和审计查询。

### 6.5 服务器能力字段

服务器记录新增代理上报的 `agent_os`、`agent_arch` 和 `agent_capabilities`。支持本设计的代理至少声明 `self_upgrade_v1`；没有声明该能力的旧代理仍可正常执行任务，但控制台显示“需人工升级基线”，不能被加入升级计划。

## 7. 升级计划编排

### 7.1 创建计划

管理员选择可用目标版本和服务器。服务端验证：

- 没有其他运行中的升级计划；
- 目标版本仍可用；
- 目标版本声明 `self_upgrade_v1`；
- 服务器已启用且架构有对应安装包；
- 服务器已经上报 `self_upgrade_v1` 能力；
- 服务器没有处于其他升级目标中；
- 服务器当前版本与目标版本不同。

系统按照控制台提交的服务器顺序分批，首批只放 1 台，其余按配置的后续批次大小划分。计划创建后立即开始首批。

### 7.2 排空与任务调度

目标进入 `draining` 时，控制面设置服务器排空标志。调度器不再把新任务分配给该服务器，但已经处于 `assigned`、`running` 或取消收尾阶段的任务继续执行。

控制面等待服务器运行任务数归零。超过排空超时则暂停计划，不强制取消任务，也不发送升级指令。管理员可在任务结束后继续计划，或取消尚未开始的目标。

### 7.3 批次推进

一个批次的全部目标达到 `succeeded` 后，控制面等待健康验证窗口结束并自动开始下一批。健康验证要求：

- 代理已使用原服务器身份重新连接；
- 上报版本等于目标版本；
- 连续心跳正常；
- 资源采集可用；
- 服务器没有被隔离或停用。

全部批次成功后计划进入 `succeeded`。每台成功服务器恢复升级前的排空状态：若原本不是排空状态，则恢复调度；若管理员在升级前已经手工排空，则继续保持排空。

### 7.4 暂停、继续与取消

- **暂停**：不启动新目标；正在下载、安装、重连或回滚的目标完成当前闭环。
- **继续**：重新检查计划和服务器状态，从尚未完成的当前批次继续。
- **取消**：只把 `waiting` 目标标记为取消；已经开始的目标继续完成升级或回滚。
- **重试失败节点**：管理员修复外部条件后，可对 `rolled_back` 或尚未执行命令的失败目标创建新尝试。
- **回滚成功节点**：以节点的 `source_version` 创建独立回滚操作，仍执行排空、替换、重连和健康验证。

## 8. 代理升级协议

现有 WebSocket 控制消息增加 `upgrade` 类型，包含：

- `command_id`
- `plan_id`
- `target_id`
- 目标版本
- 与代理架构匹配的不可变下载地址
- 文件名、字节数和 SHA-256
- 排空确认时间与重连超时

代理对重复的 `command_id` 必须幂等：已完成则重报结果，正在处理则重报当前阶段，不重复安装。

代理新增阶段事件：`accepted`、`downloading`、`verifying`、`installing`、`reconnecting`、`succeeded`、`rolling_back`、`rolled_back`、`failed`。事件包含安全错误码和中文可展示摘要，不包含安装包内容或服务器凭据。

心跳新增代理操作系统、架构、能力集合、当前升级命令、最近升级结果和本地可回滚版本。控制面重启或 WebSocket 断开后，可以通过心跳与数据库状态重新对账。

## 9. 节点本地升级器

代理服务继续以 `yunling-agent` 用户运行，不能直接覆盖 root 所有的 `/usr/local/bin/yunling-agent`。安装包增加独立的 systemd 一次性升级单元，由现有受限 polkit 规则允许代理启动。

升级流程：

1. 代理下载目标安装包到私有暂存目录。
2. 校验字节数、SHA-256、归档路径、包内 `agent-version` 和固定文件集合。
3. 写入只包含目标版本、暂存路径和期望摘要的升级规格。
4. 启动 root 身份的一次性升级单元。
5. 升级单元再次校验规格和安装包。
6. 保存当前二进制及必要的 systemd 资产为上一个可回滚版本。
7. 将新文件写入同目录临时文件，再原子替换正式文件。
8. 执行 `systemctl daemon-reload` 并重启代理服务。
9. 新代理携带原节点身份连接并报告目标版本和命令编号。

升级单元在重连超时或新进程启动失败时恢复上一版本并再次启动服务。本地只承诺保留升级前一个版本，足以完成本阶段的自动回滚和人工单节点回滚。

## 10. 异常与恢复

- **服务器离线**：目标保持等待；达到超时后计划暂停。
- **排空超时**：不终止任务，计划暂停，节点保持排空。
- **下载失败**：当前目标进入回滚闭环；如果尚未替换二进制，则直接清理暂存并记为 `rolled_back`。
- **摘要或归档校验失败**：拒绝安装，清理暂存，暂停计划。
- **安装后未重连**：本地升级单元恢复旧代理并重启。
- **重连版本不符**：控制面要求回滚并暂停计划。
- **控制面重启**：编排循环读取活动计划，根据数据库、连接状态和心跳恢复等待或对账。
- **代理升级中断电或重启**：本地规格和备份保留；升级单元在下次启动时完成替换或恢复旧版本。
- **自动回滚成功**：失败批次保持排空，管理员确认后重试、取消或恢复调度。
- **自动回滚失败**：目标进入 `manual_intervention`，服务器保持排空且不接收任务。

某一批出现任何失败时，计划立即进入 `paused`。此前成功批次不自动回滚，避免已经验证正常的服务器再次重启。

## 11. API 设计

管理员接口：

- `GET /api/agent-releases`：版本列表与推荐版本。
- `POST /api/agent-releases/{id}/recommend`：设置推荐版本。
- `POST /api/agent-releases/{id}/withdraw`：撤回版本，禁止用于新的升级计划；不能撤回当前推荐版本。
- `GET /api/agent-upgrades`：升级计划列表。
- `POST /api/agent-upgrades`：创建升级计划。
- `GET /api/agent-upgrades/{id}`：计划、目标和事件详情。
- `POST /api/agent-upgrades/{id}/pause`：暂停。
- `POST /api/agent-upgrades/{id}/resume`：继续。
- `POST /api/agent-upgrades/{id}/cancel`：取消未开始目标。
- `POST /api/agent-upgrades/{id}/targets/{targetId}/retry`：重试失败节点。
- `POST /api/agent-upgrades/{id}/targets/{targetId}/rollback`：回滚成功节点。

代理连接复用现有 `/api/agent/connect`，不增加公网端口。代理产物下载继续使用带版本与摘要的不可变地址。

所有修改接口复用现有管理员权限和审计中间件。普通成员可以查看版本盘点、计划和进度，但不能创建或控制升级计划。

## 12. 控制台交互

现有“服务器”模块增加页签：

- **节点管理**：保留当前服务器列表与详情抽屉。
- **代理升级**：显示版本概况、当前计划和历史记录。

节点列表增加“代理版本”列，状态显示为：已是最新版、可升级、升级中、版本未知或升级失败。

没有上报 `self_upgrade_v1` 的旧代理显示“需人工升级基线”，创建计划时不可勾选，并提供复用现有一条命令安装器的操作说明。安装器检测到有效节点身份时保留原身份，只更新代理程序和 systemd 资产。

代理升级页顶部显示：推荐版本、服务器总数、待升级数、升级中数量和异常数量。活动计划展示整体进度、当前批次以及成功、失败、等待数量。

版本仓库区域显示每个版本的状态、发布说明、架构和时间。管理员可以把可用版本设为推荐版本，或撤回非推荐版本；撤回不会删除安装包和历史记录。

创建计划采用三步向导：

1. 选择目标版本并查看中文发布说明。
2. 选择服务器，可按云厂商、地域、标签和当前版本筛选。
3. 确认首批 1 台、后续批次大小、排空超时、重连超时与健康验证时间。

计划详情以表格和时间线展示每台服务器的阶段。可用操作包括暂停、继续、取消未开始节点、重试失败节点和回滚指定成功节点。所有危险操作均明确显示实际影响范围。

## 13. 可观测性与审计

升级事件至少记录：计划、服务器、源版本、目标版本、批次、阶段、开始时间、结束时间、尝试次数和安全错误摘要。

审计动作包括：导入版本、设置推荐版本、创建计划、暂停、继续、取消、重试、人工回滚和恢复调度。日志和 API 响应不记录代理凭据或安装包正文。

运行总览可以增加“代理待升级”和“升级异常”提示，但不在本阶段重做总览页面。

## 14. 测试策略

### 14.1 后端与状态机

- 版本导入拒绝缺失架构、重复版本、错误摘要和版本不一致。
- 创建计划正确生成首批 1 台和后续批次。
- 同时只能存在一个活动计划。
- 排空后不再分配新任务，现有任务结束后才发送升级指令。
- 批次全部健康后自动推进；任一失败立即暂停。
- 失败批次回滚，而此前成功批次保持新版本。
- 暂停、继续、取消未开始目标和重试均保持幂等。
- 控制面重启后从数据库恢复计划并根据心跳对账。

### 14.2 代理与本地升级器

- 正确下载、校验、暂存和应用匹配架构的安装包。
- 重复命令不重复替换代理。
- 原子替换后原服务器身份、配置和脚本缓存保持不变。
- 新代理重连并上报目标版本后成功结束。
- 新代理无法启动、重连超时或版本不符时恢复旧版本。
- 升级进程中断后能从本地规格恢复或回滚。

### 14.3 Web

- 节点管理正确显示代理版本状态。
- 创建计划向导完成版本、服务器和批次配置。
- 有活动计划时禁止创建第二个计划。
- 中文阶段、进度、失败摘要和按钮可随状态正确变化。
- 暂停、继续、取消、重试与回滚操作正确刷新详情。
- 键盘焦点、对话框关闭、移动端表格和空状态保持可用。

### 14.4 集成验收

- 使用两个临时 Linux 节点验证从旧版本到新版本的分批升级。
- 在首台节点运行任务时启动计划，确认等待任务结束且任务不中断。
- 注入首批成功、下一批失败场景，确认计划暂停且只回滚失败批次。
- 在下载、安装、重连阶段分别重启控制面或代理，确认流程可恢复。
- 回滚完成后确认旧版本重新连接并恢复调度。

## 15. 上线与兼容

先发布支持新协议但不创建升级计划的代理版本，再发布控制面与数据库迁移。新控制面必须继续兼容不认识升级指令的旧代理：旧代理只参与版本盘点，不会收到升级命令。

现有旧节点需要执行一次人工基线更新，安装器复用节点原有身份，不重新注册。完成这一次更新并上报 `self_upgrade_v1` 后，后续版本才全部通过控制台升级。未来新接入服务器默认安装具备升级器的推荐版本，不再需要此基线步骤。

正式启用顺序：

1. 数据库迁移后由 API 把现有只读发布目录导入为推荐基线，确认新服务器接入接口持续可用。
2. 导入第一个具备升级器的代理版本。
3. 在现有节点逐台人工安装该版本作为升级基线，先从一台非关键节点验证；节点身份和配置保持不变。
4. 验证控制面版本盘点和升级协议。
5. 导入下一测试版本，用单节点计划完成升级与回滚验收。
6. 验收通过后开放生产升级计划入口。

数据库迁移只新增表、索引和必要字段，不破坏现有服务器、任务、脚本、日志或凭据记录。控制台和 API 回滚后，已经升级成功的代理继续兼容旧控制面；活动计划在数据库中保留，待功能恢复后继续处理。

## 16. 完成标准

本阶段只有同时满足以下条件才算完成：

- 控制台能够统一盘点服务器代理版本，并显示是否可升级。
- 多版本仓库能保存、查询和下载两个 Linux 架构的不可变版本。
- 管理员能够创建首批 1 台、后续自动推进的分批升级计划。
- 升级前自动排空且不终止正在运行的任务。
- 代理无需 SSH 即可完成下载、校验、原子替换、重启和结果上报。
- 任一失败会暂停计划并自动回滚失败批次，此前成功批次保持新版本。
- 控制面或代理重启后可以恢复或对账，不产生重复安装。
- 成功节点恢复原调度状态，回滚失败节点保持排空并明确提示人工处理。
- 后端、代理、Web 与端到端测试全部通过，所有面向用户的文案为中文。
