# 云令版本化构建与人工批准生产发布设计

## 1. 背景

云令已经在腾讯云运行控制面，在京东云运行首个执行代理。仓库现已建立五项 GitHub Actions CI 质量门禁和 `main` 分支保护，但生产发布仍依赖人工进入服务器、上传或拉取源码、现场构建镜像并重建容器。这种方式无法证明线上版本对应哪个提交，也缺少统一审批、不可变产物、自动健康检查和可靠回滚。

本阶段在现有 CI 之后增加版本化候选构建与人工批准的生产发布。首版仅更新腾讯云控制面应用，不迁移数据库、不替换基础设施容器、不升级京东云代理。

## 2. 已确认决策

- 发布范围仅包含腾讯云控制面应用。
- 使用 GitHub 托管 Runner，不在生产机安装自托管 Runner。
- 候选镜像发布到 GitHub Container Registry（GHCR），生产按不可变镜像摘要拉取。
- `main` 通过 CI 后自动生成候选版本；上线时人工选择候选并批准。
- GitHub Actions 通过专用、受限的 SSH 部署账号触发生产机固定发布程序。
- 允许应用更新期间出现约 30 至 60 秒短暂中断，不建设蓝绿环境。
- 新版本健康检查失败时立即恢复上一成功版本，不重复尝试失败版本，并发送飞书告警。
- 首版不执行数据库迁移，也不改变已发布代理包。

## 3. 目标

- 每个通过 `main` CI 的提交都能产生可追溯、可验证的候选版本。
- 候选版本用源提交、GitHub 运行编号和三个镜像 SHA-256 摘要唯一标识。
- 生产发布必须经过 GitHub `production` 环境人工审批。
- 审批前不读取生产 SSH 私钥或飞书发布通知密钥。
- 生产机不再拉取 Git 源码或现场构建应用镜像。
- 发布只替换 `api`、`scheduler`、`web`、`ops` 四个应用容器。
- 发布前完成来源、兼容性、基础设施健康和资源检查。
- 发布后同时验证容器、内部接口和公网入口。
- 任一发布检查失败时自动恢复上一成功版本，并保留可安全查看的诊断信息。
- 支持人工选择历史成功版本回滚，以处理延迟暴露的故障。

## 4. 非目标

- 不更新 PostgreSQL、Redis、MinIO 或 Caddy 镜像与配置。
- 不执行、生成或自动应用数据库迁移。
- 不升级、灰度发布或自动回滚京东云代理。
- 不把生产发布入口集成到云令 Web 控制台。
- 不建设多生产环境、蓝绿环境或 Kubernetes 集群。
- 不在生产机保存 GitHub 仓库写令牌。
- 不自动清理 GHCR 中的历史镜像。
- 不把 `.env`、运行时密钥或服务器凭据放入镜像、构建产物或日志。

## 5. 总体架构

发布链路分为相互隔离的两段：候选构建和生产部署。

```text
main 的“云令 CI”成功
        |
        v
候选构建工作流
        |
        +-- GHCR：services / web / ops 不可变镜像
        |
        `-- Actions Artifact：release-manifest.json
                              |
                              v
人工触发生产工作流并选择候选运行编号
                              |
                              v
GitHub production 环境审批
                              |
                              v
受限 SSH 密钥 -> 腾讯云固定发布程序
                              |
                 +------------+-------------+
                 |                          |
              检查通过                   检查失败
                 |                          |
          保存为当前成功版本        恢复上一成功版本
                 |                          |
                 `-----------飞书通知-------'
```

候选构建没有生产凭据，也不能连接腾讯云。生产部署任务只有在 GitHub 环境保护规则通过后才能取得环境密钥。生产机上的 SSH 公钥使用强制命令和连接限制，不能打开普通终端。

## 6. 候选版本

### 6.1 触发与信任边界

新增独立候选构建工作流，只监听名为 `云令 CI` 的 `workflow_run.completed` 事件。工作流在开始构建前必须同时验证：

- 上游运行结论为 `success`；
- 上游仓库 ID 与当前仓库 ID 完全相同；
- 上游分支为 `main`；
- 上游事件为 `push`；
- 检出提交严格等于上游运行的 `head_sha`。

候选工作流只使用默认分支上受信任的工作流定义，不执行 Pull Request 分支中的候选发布逻辑。相同源提交只保留一个正常自动候选构建；人工重跑可以生成新的运行编号，每次运行都以自己的发布清单和实际镜像摘要独立标识。

### 6.2 镜像集合

首版发布三个 Linux amd64 镜像：

- `ghcr.io/nolyone1/yunling-services`：供 `api` 与 `scheduler` 共用，并保留 `bootstrap` 可执行文件但生产发布不运行 bootstrap；该镜像不再内置代理可执行文件或代理发布包；
- `ghcr.io/nolyone1/yunling-web`：中文 Web 控制台；
- `ghcr.io/nolyone1/yunling-ops`：备份、恢复校验、告警与运维健康服务。

镜像可以附加便于阅读的 `sha-<完整提交>` 标签，但标签只用于发现候选。发布清单和生产 Compose 必须使用 `名称@sha256:<摘要>`，不得使用 `latest` 或其他可移动标签。

仓库本身公开，因此三个 GHCR 包设为公开。生产机按摘要匿名拉取，避免保存长期 `read:packages` 令牌。镜像构建上下文由 `.dockerignore` 限制；构建测试必须证明 `.env`、`deploy/secrets`、SSH 文件和本地备份不会进入镜像层。

所有 Dockerfile 的基础镜像必须固定到 SHA-256 摘要。Go 与 npm 依赖继续由锁文件约束，候选构建不得用未固定版本的下载脚本动态安装程序。镜像自身无需承诺跨运行摘要相同；不可变性以每次候选清单记录的实际摘要为准。

### 6.3 发布清单

候选工作流生成单一 `release-manifest.json`。格式版本固定为整数 `1`，至少包含：

```json
{
  "schema_version": 1,
  "candidate_run_id": 123456789,
  "repository_id": 123456789,
  "source_sha": "40位小写Git提交摘要",
  "created_at": "RFC3339 UTC时间",
  "images": {
    "services": "ghcr.io/nolyone1/yunling-services@sha256:64位摘要",
    "web": "ghcr.io/nolyone1/yunling-web@sha256:64位摘要",
    "ops": "ghcr.io/nolyone1/yunling-ops@sha256:64位摘要"
  },
  "compatibility": {
    "migration_tree_sha256": "64位摘要",
    "deployment_contract_sha256": "64位摘要",
    "agent_version": "0.1.0",
    "agent_manifest_sha256": "64位摘要"
  }
}
```

`migration_tree_sha256` 是对排序后的迁移相对路径和各文件 SHA-256 进行规范化拼接后再次计算的摘要。`deployment_contract_sha256` 覆盖生产基础 Compose 和固定发布约束。生产程序只接受与当前基线相同的这两个摘要，借此拒绝夹带数据库或基础设施配置变化的候选。

`agent_manifest_sha256` 来自仓库内只记录版本、文件名、大小和摘要、不保存二进制的 `deploy/agent/release-lock.json`，其值对应代理卷中原始 `manifest.json` 的字节摘要。公网 `/api/releases/agent/latest` 会由 API 为每个归档动态增加 `download_url`，因此公网响应本身具有不同的字节摘要，不能直接与 `agent_manifest_sha256` 比较；公网只读核验必须先删除这个唯一派生字段，并按 `package.sh` 的确定字段顺序和末尾换行重建原始清单，同时独立下载两个归档核对大小和摘要。首次生产导入时则直接复制并校验容器内原始文件，不依赖重建。该锁文件随实施 Pull Request 接受审核。现有生产代理清单和两个包在首次启用时原样复制到独立命名卷 `yunling_agent_releases`，API 以只读方式挂载。生产程序校验卷内清单、包大小和包摘要均与锁文件一致；候选控制面镜像自身不包含代理发布文件，因此普通控制面发布没有改变代理下载内容的能力。未来代理升级必须通过独立流程同时更新命名卷和锁文件。

新的控制面环境必须先从经过独立批准且与锁文件一致的代理发布来源初始化该命名卷，API 才允许启用代理下载接口。本阶段只迁移现有腾讯云生产内容，不建设通用代理发布来源；该能力归入后续代理发布阶段。

清单作为名称含源提交的 GitHub Actions Artifact 保存 90 天。上传步骤返回的 Artifact 摘要写入工作流摘要。已部署清单另由生产机长期保存，因此 Actions Artifact 到期不影响当前版本或自动回滚。

### 6.4 供应链证明与权限

候选工作流权限按 Job 分开：默认只有 `contents: read`；推送镜像的 Job 增加 `packages: write`；生成来源证明的 Job 增加 `attestations: write` 与 `id-token: write`。不得授予仓库内容写权限、部署权限或 Actions 管理权限。

每个镜像生成与精确摘要绑定的 GitHub Artifact Attestation。所有 GitHub 官方和第三方 Action 固定到完整提交 SHA，不引用可移动标签。

## 7. 生产审批与候选选择

新增只支持 `workflow_dispatch` 的生产工作流，输入为操作类型和目标标识：

- `deploy`：目标标识必须是十进制候选运行编号，部署该候选对应的版本；
- `rollback`：目标标识可以是历史成功候选运行编号，也可以是保留字 `bootstrap`，后者只表示首次启用时导入的本地基线。

`deploy` 操作的无密钥预检 Job 先通过 GitHub API 读取候选运行，验证工作流名称、仓库 ID、`main`、`push`、成功结论和 Artifact 名称，再下载并校验清单格式、源提交和 Artifact 摘要。任何字段不一致都在审批前失败。`rollback` 操作在审批前只校验目标是十进制运行编号或 `bootstrap`；审批后由生产机确认目标确实存在于本地成功历史中，因此 Actions Artifact 到期不妨碍历史回滚。

实际发布 Job 引用 `production` 环境并使用固定并发组 `production-release`，`cancel-in-progress` 为 `false`。这样一个发布执行期间，后续发布只能等待，不能取消正在操作生产容器的任务。

`production` 环境配置一名必需审核人，并只允许受保护的 `main` 分支部署。当前只有一名发布人时允许发起者本人审核；团队增加第二名生产管理员后，开启 GitHub 的“禁止自我审核”。生产环境禁止管理员绕过保护规则。

## 8. 生产凭据与 SSH 限制

生产环境仅保存：

- 新生成的专用 Ed25519 部署私钥；
- 固定的腾讯云 SSH 主机公钥指纹或完整 `known_hosts` 记录；
- 独立的飞书发布通知地址；
- 不敏感的生产主机和部署用户名使用环境变量保存。

不得复用日常登录密钥、root 密钥或服务器密码。SSH 客户端必须启用严格主机密钥检查，禁止首次连接自动接受未知主机。

生产机创建无密码、无普通管理权限的 `yunling-deploy` 用户。该公钥在 `authorized_keys` 中使用 `restrict` 和强制命令，只允许调用 root 所有且普通用户不可写的入口。入口再通过精确 sudoers 规则调用固定发布程序；不允许 Shell、PTY、端口转发、代理转发、X11 转发、任意 `docker` 命令或任意路径脚本。

发布程序从标准输入接收候选清单和一个独立的部署请求信封；信封只包含操作类型、目标运行编号、GitHub 操作者、生产工作流运行编号和运行链接。程序不信任 `SSH_ORIGINAL_COMMAND` 中的自由文本，并对所有路径、镜像名称、摘要、操作类型、链接域名和数字长度执行白名单校验。审计中的操作者是可追溯元数据，不用于代替 GitHub 环境审批做授权决定。

## 9. 生产文件与状态

首次启用时把固定发布程序、生产 Compose 基线和受限 SSH 配置安装为 root 所有。后续普通应用发布不能替换这些文件。生产应用继续位于 `/opt/yunling`，其中：

- `deploy/docker-compose.yml`：当前生产基础定义和运行时环境引用；
- `deploy/docker-compose.release.yml`：由发布程序原子生成，只包含四个应用服务的三个镜像摘要；
- `yunling_agent_releases` 命名卷：保存首次启用前已经公开的代理清单和两个安装包，只读挂载给 API；
- `releases/<候选运行编号>/release-manifest.json`：通过校验的候选历史清单；
- `releases/bootstrap/release-manifest.json`：首次启用时由本机生成的生产基线，不接受远程覆盖；
- `releases/current.json`：当前成功清单；
- `releases/previous.json`：上一成功清单；
- `releases/audit.jsonl`：追加写审计记录；
- `releases/diagnostics/<时间>-<运行编号>/`：经过脱敏的失败诊断。

`.env`、`deploy/secrets`、数据库卷、对象存储卷和备份数据不移动，也不复制到发布目录。清单和状态文件先写临时文件、`fsync`，再在同一文件系统内原子改名，避免中途断电留下半份状态。

首次启用需要从当前运行容器和 Compose 配置导入初始 `current.json`，同时记录迁移树、部署契约和代理发布基线摘要。安装程序先从当前 API 容器逐字节复制已经公开的代理清单和两个安装包，重新校验大小与 SHA-256 后写入 `yunling_agent_releases`，再把卷只读挂载给 API；原容器与新挂载返回的公开清单和包摘要必须完全一致。

安装程序还分别捕获 `api`、`scheduler`、`web`、`ops` 四个当前运行容器的本地镜像 ID，并为每个镜像创建 root 管理的只读基线标签。当前 API 与 Scheduler 可能来自不同构建，初始清单不得把两者错误合并。该清单标记为 `local-bootstrap`；这种本地引用只能由安装程序生成，远程请求永远不能提交。第一次 GHCR 发布失败时可以据此恢复四个原容器。完成第一次和第二次成功 GHCR 发布后，`current` 与 `previous` 都会自然变为 GHCR 摘要。没有初始成功基线或代理卷校验失败时，程序只允许 `preflight`，拒绝实际更新。

## 10. 发布算法

固定发布程序按以下顺序执行：

1. 使用 `flock` 获取单机独占锁；锁已占用时直接拒绝，不等待第二个发布。
2. 以不包含秘密的方式记录操作者、GitHub 运行编号、源提交和开始时间。
3. 严格解析清单，拒绝任意层级的未知字段、重复 JSON 键、非允许仓库、标签引用、非小写摘要和超长输入。
4. 比较生产基线的迁移树、部署契约和代理清单摘要；任一不相同即拒绝。
5. 确认 Docker daemon、Compose 插件和四个基础设施服务可用。
6. 确认可用磁盘至少 3 GiB，`MemAvailable` 至少 512 MiB；不足时不改变容器。
7. 按摘要拉取三个镜像，并用本地镜像检查再次确认实际摘要。
8. 把当前成功清单复制为本次回滚目标，原子生成只包含目标摘要的 Compose 覆盖文件。
9. 使用 `docker compose ... up -d --no-deps --no-build api scheduler web ops` 重建四个应用容器，不启动 `bootstrap`。
10. 在两分钟期限内执行完整健康检查。
11. 成功时原子更新 `previous.json` 和 `current.json`，追加成功审计记录，并把机器可读结果返回给 GitHub Job 发送飞书成功通知。

拉取、资源或兼容性预检失败发生在容器变化前，因此不需要回滚。容器开始变化后的任何失败都进入自动回滚。

## 11. 健康检查

两分钟总期限内，每五秒检查一次，所有条件必须在同一次检查周期中满足：

- `api`、`scheduler`、`web`、`ops` 容器存在且状态为 healthy；
- API 容器内部 `/api/health` 返回成功并包含预期健康标记；
- Web 容器内部 `/healthz` 返回 `ok`；
- Ops 容器内部 `/healthz` 返回 `ok`；
- 通过公网域名访问 `/healthz` 成功；
- 通过公网域名访问 `/api/health` 成功。

公网检查必须验证 TLS，不允许 `curl -k`。响应体和状态码设长度上限，不能把页面、环境或错误堆栈整体打印到日志。Scheduler 没有 HTTP 接口，继续使用现有容器存活健康检查。

## 12. 自动与人工回滚

容器更新后的健康检查失败时，程序立即：

1. 保存四个应用容器最后 200 行、最多 1 MiB 的脱敏日志和 `docker compose ps`；
2. 用发布前保存的成功清单重新生成 Compose 覆盖文件；
3. 按上一成功摘要重建四个应用容器；
4. 使用与发布相同的两分钟健康检查验证恢复结果；
5. 追加失败审计记录，并把发布与回滚结果返回给 GitHub Job 发送飞书通知。

自动回滚不需要第二次人工批准，因为它属于已批准发布事务的恢复步骤。自动回滚成功时，`current.json` 保持原值；失败候选只进入审计记录，不能成为 `previous.json`。

自动回滚也失败时，工作流以严重故障结束，保留新旧目标摘要、容器状态和脱敏诊断路径。程序不得删除数据卷、重建基础设施或尝试数据库恢复。

人工回滚只能选择生产机 `releases/` 中标记为成功且摘要完整的历史清单，也必须经过 `production` 环境审批。在第二个 GHCR 版本稳定前允许选择只读 `bootstrap` 基线；其后仍保留该基线用于灾难排查，但日常回滚优先选择 GHCR 摘要版本。人工回滚完成后，目标历史版本成为新的 `current`，回滚前版本成为 `previous`。

## 13. 飞书通知与审计

生产工作流发送中文通知，至少包含：

- 操作类型；
- GitHub 操作者；
- 候选运行编号和源提交短摘要；
- 开始、成功或失败时间；
- 三个镜像摘要短值；
- 发布、自动回滚或人工回滚结果；
- GitHub 工作流运行链接；
- 生产诊断编号，不包含服务器绝对秘密路径。

飞书通知由审批后的 GitHub Job 发送，通知地址不传入腾讯云。通知失败不能把已经健康的应用判为发布失败，但必须使通知步骤显示警告，并在 GitHub 摘要中记录 `notification_failed`；生产机本地审计只记录其能够证明的发布和回滚结果。发布失败或回滚失败时仍以部署结果决定工作流失败状态。

审计日志不得记录 SSH 私钥、环境密钥、`.env`、数据库连接串、飞书完整地址、Cookie、访问令牌或代理注册令牌。工作流不得开启全局 Shell 跟踪，也不得输出完整环境变量集合。

## 14. 测试设计

### 14.1 清单与规范化单元测试

- 接受唯一合法的版本 1 清单。
- 拒绝未知字段、重复键、缺失字段、错误仓库、可移动标签、大写或长度错误的摘要。
- 证明迁移树和部署契约摘要不受文件枚举顺序影响，但任一字节变化都会改变摘要。
- 证明代理锁文件能够校验版本、清单、两个包的文件名、大小和摘要，并拒绝任何漂移。

### 14.2 发布程序测试

使用临时目录和记录调用的 Docker、Compose、curl、flock 替身覆盖：

- 锁冲突；
- 磁盘或内存不足；
- 基础设施不健康；
- 镜像拉取失败或摘要不一致；
- 兼容性摘要不一致；
- 四个应用分别失败；
- 公网检查失败；
- 自动回滚成功；
- 自动回滚失败；
- 状态文件原子更新和审计脱敏；
- 人工回滚拒绝未知或失败版本。

### 14.3 Compose 与工作流契约测试

- 完整解析基础 Compose 和发布覆盖文件。
- 断言发布覆盖只允许 `api`、`scheduler`、`web`、`ops` 的 `image` 字段。
- 断言生产命令包含 `--no-deps` 与 `--no-build`，且不包含 `down`、卷删除、数据库迁移或 bootstrap。
- 断言候选只源自成功的 `main` push CI。
- 断言生产工作流只有手动触发，引用 `production` 环境，禁用运行中取消并使用固定并发组。
- 断言所有 Action 固定 SHA，权限满足最小集合，Secrets 只出现在审批后的发布 Job。

### 14.4 镜像与集成测试

- 构建并扫描三个目标镜像的层和文件列表，确认不包含秘密文件。
- 证明 `yunling-services` 镜像不包含代理可执行文件和代理发布包，API 只能从只读命名卷读取锁定发布内容。
- 启动隔离 Compose 环境，按摘要完成一次成功更新。
- 在隔离环境注入无法健康的 Web 或 API 镜像，证明两分钟内恢复上一版本。
- 证明更新前后的数据库卷、Redis、MinIO 和 Caddy 容器 ID 不变。
- 证明京东云代理不会收到升级命令，公开代理清单和包摘要保持不变。

## 15. 首次启用顺序

1. 在取得当时的只读生产访问确认后，读取当前代理发布清单与两个包的大小和摘要，生成不含二进制的代理锁文件。
2. 在新功能分支完成工作流、发布程序、测试和中文运维文档。
3. 通过 Pull Request 和现有五项质量门禁合并到 `main`。
4. 首次候选构建成功后，把三个 GHCR 包设为公开，并验证匿名按摘要拉取。
5. 在 GitHub 创建 `production` 环境，设置必需审核人、仅允许受保护分支、禁止管理员绕过，并写入专用环境密钥。
6. 生成全新的 Ed25519 部署密钥；在腾讯云创建受限用户、强制命令和精确 sudoers 规则。
7. 从当前 API 容器把现有代理清单和安装包原样迁入只读命名卷，并验证迁移前后公开内容与已审核锁文件完全一致。
8. 安装 root 所有的固定发布程序与 Compose 基线，为当前四个应用容器分别建立只读本地镜像标签，并导入当前生产版本作为初始成功基线。
9. 运行只读 `preflight`，确认主机指纹、权限、资源、基础服务和三个兼容性摘要。
10. 在隔离 Compose 环境完成首个候选的成功更新、失败注入和自动回滚演练。
11. 分别对比首个候选与生产 API、Scheduler、Web、Ops 的现有代码基线和镜像摘要，向用户展示差异并再次取得生产发布确认。
12. 发布首个候选到生产，验证四个应用、代理下载内容、状态文件、审计记录和飞书通知。

生产环境设置、GHCR 可见性和腾讯云账号安装都是仓库外操作，必须逐项取得用户当时确认，不能因本设计获批而自动执行。

## 16. 验收标准

- `main` CI 成功后自动生成三个 GHCR 候选镜像、来源证明和单一发布清单。
- 失败、取消、Pull Request 或外部仓库 CI 不会生成候选。
- 人工可以用候选运行编号选择版本，审批前发布 Job 无法读取生产 Secrets。
- 同一时间最多一个生产发布运行，后续发布不会取消正在进行的发布。
- 腾讯云只按清单中的三个镜像摘要拉取，不拉源码、不现场构建。
- 发布只重建四个应用容器，数据库、Redis、MinIO、Caddy 和数据卷保持不变。
- 数据库迁移、部署契约或代理清单摘要变化会在容器更新前阻断发布。
- 控制面镜像不携带代理发布内容，API 公开的代理版本和包摘要在发布前后完全一致。
- 成功发布通过四个容器、三个内部接口和两个公网入口检查，并写入当前状态和审计记录。
- 失败发布能在规定期限内恢复上一成功版本并发送飞书告警。
- 人工回滚只能选择历史成功版本并同样经过生产审批。
- 自动化测试覆盖成功、预检失败、发布失败、回滚成功和回滚失败路径。
- 所有操作文档、工作流显示名称、步骤名称和通知内容使用中文。

## 17. 风险与控制

### 17.1 GitHub 或 GHCR 不可用

候选构建或镜像拉取失败发生在容器变化前，生产保持现状。已经拉取到生产机的当前与上一成功镜像可用于本地恢复。首版不因外部平台故障绕过审批或改为现场构建。

### 17.2 单机更新产生短暂中断

当前腾讯云资源不适合同时运行完整蓝绿副本。发布保留 Caddy 和基础设施，只重建四个应用容器，并把总健康期限限制为两分钟。需要近零中断时必须先扩容，再独立设计蓝绿发布。

### 17.3 受信任代码仍可能包含恶意镜像行为

分支保护、五项 CI、固定来源提交、镜像证明和人工生产审批共同降低风险。审批人必须检查候选提交与 CI 结果；审批不是自动确认步骤。

### 17.4 Actions Artifact 到期

未部署候选在 90 天后不再允许首次部署。成功部署清单由生产机长期保留，GHCR 镜像首版不自动清理，因此当前版本和历史成功版本仍可回滚。后续增加清理策略时必须保护 `current`、`previous` 和审计中引用的摘要。

### 17.5 飞书通道故障

飞书故障不回滚健康版本，也不掩盖部署失败。GitHub 工作流结论、部署历史和生产审计是独立记录渠道。

## 18. 后续阶段

本阶段稳定后，依次独立设计：

- 发布前数据库备份、显式数据库迁移、迁移兼容窗口和数据恢复决策；
- 代理版本盘点、独立代理产物、灰度升级、自动分批和代理回滚；

- 云令控制台中的只读发布历史和运行状态展示。
