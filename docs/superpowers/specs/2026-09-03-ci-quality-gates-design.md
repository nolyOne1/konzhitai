# 云令 CI 质量门禁设计

## 1. 背景

云令已经完成全中文脚本管理、多服务器代理、资源调度、排队、脚本同步、团队权限、飞书通知和备份恢复，并已部署到腾讯云。当前 GitHub 仓库尚未配置持续集成，Pull Request 可以在没有自动检查的情况下合并，`main` 也没有强制质量门禁。

本阶段建立一套只负责验证、不负责部署的 GitHub Actions 流程。它在代码进入 `main` 前运行完整检查，并通过 GitHub 分支保护阻止未通过检查的变更合并。

## 2. 目标

- 在面向 `main` 的 Pull Request 上自动运行完整质量检查。
- 在提交进入 `main` 后重新运行同一套检查，验证默认分支状态。
- 并行覆盖 Go、Web、Playwright、代理安装包和生产部署配置。
- 检查过程不读取生产密钥，不连接腾讯云、京东云、飞书或 COS。
- 将五项稳定命名的检查设为 `main` 的必需状态。
- 禁止直接推送、强制推送和删除 `main`；当前不要求其他成员批准。
- 为失败任务保留足够的安全诊断信息，同时避免日志和产物泄露凭据。

## 3. 非目标

- 不自动部署、重启或修改腾讯云生产环境。
- 不连接京东云执行节点，也不运行真实脚本任务。
- 不在 GitHub 中保存 SSH、数据库、飞书、COS 或恢复密钥。
- 不引入腾讯云自托管 Runner。
- 不在本阶段实现代理灰度升级、自动升级或回滚。
- 不要求代码所有者审核，也不要求固定审核人数；团队扩大后单独启用。
- 不改变云令应用、调度器、代理或数据库的运行行为。

## 4. 方案选择

采用 GitHub 托管的 Ubuntu Runner，并把质量门禁拆分为五个并行任务。相比单一串行任务，这种结构能更快反馈，并让失败直接对应具体子系统。相比腾讯云自托管 Runner，它不持有生产网络权限，也不会让不受信任的 Pull Request 代码接触生产服务器。

CI 使用一个仓库内工作流文件 `.github/workflows/ci.yml`。所有任务在干净 Runner 上执行，任务之间不传递可执行产物，也不共享工作目录；只使用依赖缓存和失败诊断产物。

## 5. 触发与并发控制

工作流支持以下事件：

- `pull_request`：目标分支为 `main`，覆盖创建、重新打开和新提交同步。
- `push`：分支为 `main`，用于合并后复验。
- `workflow_dispatch`：仅用于人工重新运行质量检查，不包含任何部署输入。

同一个 Pull Request 或同一个分支只保留最新运行。并发组由工作流名称和 Pull Request 编号或 Git 引用组成，`cancel-in-progress` 设为 `true`。旧提交被取消不算新提交通过；分支保护只读取当前提交上的五项必需检查。

## 6. 权限与供应链边界

工作流顶层权限固定为：

```yaml
permissions:
  contents: read
```

设计约束如下：

- 不使用 `pull_request_target`，避免来自 Fork 的代码取得默认分支上下文或更高权限。
- 不声明 `id-token`、`packages`、`deployments`、`actions: write` 或其他写权限。
- 不读取仓库、环境或组织 Secrets。
- 不调用生产域名、腾讯云、京东云、飞书或 COS 接口。
- GitHub 官方 Action 和其他 Action 都固定到完整提交 SHA，并在行尾注释对应版本，禁止只使用可移动标签。
- Go 与 npm 依赖继续由 `go.sum` 和 `package-lock.json` 校验；缓存键包含对应锁文件哈希。
- 不把分支名、Pull Request 标题、提交消息或其他不可信文本拼接进 Shell 命令、路径或产物名称。
- 失败产物只允许包含 Playwright 报告、截图和 Trace，不上传 `.env`、日志数据库、代理凭据或工作区整体压缩包。

## 7. 五项必需检查

工作流的 Job 标识保持稳定，显示名称使用中文。启用分支保护后不得随意改名；如确需改名，应先调整保护规则，再修改工作流，避免所有 Pull Request 因等待不存在的检查而无法合并。

### 7.1 `后端测试与构建`

- Runner：Ubuntu。
- 工具链：Go 1.27，版本来源与 `go.mod` 一致。
- 使用 Go 模块和构建缓存。
- 执行 `go test -race -p=1 ./... -count=1`。
- `-race` 覆盖调度、心跳、同步、日志和通知等并发路径。
- `-p=1` 避免多个测试包同时初始化共享的嵌入式 PostgreSQL 缓存。
- 测试成功后，以 `CGO_ENABLED=0` 编译 API、Scheduler、Ops、Agent 和 Bootstrap。
- 超时 30 分钟。

### 7.2 `前端测试与构建`

- Runner：Ubuntu。
- 工具链：Node.js 24，满足根 `package.json` 的引擎约束。
- 使用 npm 缓存，缓存键由 `package-lock.json` 决定。
- 执行 `npm ci`，禁止在 CI 中改写锁文件。
- 执行 Web 单元测试和组件测试。
- 执行 TypeScript 与 Vite 生产构建。
- 超时 15 分钟。

### 7.3 `端到端测试`

- Runner：Ubuntu。
- 工具链：Node.js 24。
- 执行 `npm ci`。
- 按项目已锁定的 Playwright 版本安装 Chromium 及所需系统依赖。
- 执行现有 5 项 Playwright 流程；由项目配置启动本地 Vite 服务，不设置 `YUNLING_E2E_BASE_URL`，因此不会访问生产环境。
- 保留项目现有的 CI 重试、中文区域、上海时区、失败截图和 Trace 配置。
- 失败或取消时上传 Playwright 报告、截图和 Trace，保留 7 天；成功时不上传诊断产物。
- 超时 20 分钟。

### 7.4 `代理安装与打包`

- Runner：Ubuntu。
- 工具链：Go 1.27，用于真实生成 Linux amd64 与 arm64 代理二进制。
- 先对 `deploy/agent/install.sh`、`package.sh` 和相关脚本执行 Shell 语法检查。
- 运行 `deploy/agent/install_test.sh`，验证地址校验、令牌不泄露、失败清理、注册后恢复和已有身份修复。
- 运行 `deploy/agent/package_test.sh`，验证不可变安装包内容、清单、大小和 SHA-256。
- 执行一次真实的 Linux amd64 与 arm64 代理交叉编译和打包，校验发布清单，不上传发布包。
- 超时 15 分钟。

### 7.5 `部署配置与镜像`

- Runner：Ubuntu，使用 GitHub 托管 Runner 自带的 Docker 与 Compose。
- 使用 `deploy/.env.example` 校验 `deploy/docker-compose.yml` 的完整解析结果。
- 验证仓库中的部署脚本保留 LF 换行，避免 Linux shebang、systemd 和字符串边界测试在 Windows 检出后失效。
- 构建 Web、API、Scheduler、Ops 和 Bootstrap 等云令应用镜像。
- 不启动 Compose，不创建数据卷，不执行数据库迁移，不构建或运行生产服务。
- MinIO 固定源码镜像不纳入每次 Pull Request 的应用镜像构建；其 Dockerfile 和 Compose 引用仍由现有集成测试与配置解析覆盖。需要升级 MinIO 时单独设计供应链验证。
- 超时 30 分钟。

## 8. 失败处理与诊断

- 五个任务相互独立，并行运行；一个任务失败不主动取消其他任务，使一次运行能展示全部问题。
- 每个任务使用明确的中文显示名称和步骤名称，GitHub 摘要可以直接定位失败阶段。
- 命令保持默认错误退出行为，不使用掩盖失败的 `continue-on-error`。
- Playwright 失败诊断使用固定、无用户输入的产物名称，并限制保留时间为 7 天。
- Go、npm、Shell 或 Docker 输出直接进入 GitHub 日志，但工作流不得开启全局 Shell 跟踪，也不得输出环境变量集合。
- 外部依赖下载失败与测试失败在步骤名称上分开，便于区分基础设施故障和代码回归。
- Runner 或 GitHub Actions 平台故障时允许人工重新运行；不得通过修改测试命令、跳过 Job 或直接推送 `main` 绕过。

## 9. `main` 分支保护

第一次 Pull Request 上五项检查全部成功并在 GitHub 中出现稳定名称后，启用针对 `main` 的规则：

- 必须通过 Pull Request 合并。
- 必须通过上述五项检查。
- 合并前分支必须与 `main` 保持最新。
- 必须解决所有审查对话。
- 审核批准数保持为 0，避免当前单人维护时自我审批阻塞。
- 禁止直接推送、强制推送和删除分支。
- 不允许普通成员绕过规则；仓库所有者如遇 GitHub 平台级故障，应先临时调整规则并留下可审计说明，恢复后立即重新启用。

保护规则属于 GitHub 仓库设置，不写入应用配置。如果现有 GitHub 集成没有管理规则的权限，由用户在仓库“设置 → 分支/规则”中按上述值完成，随后用只读接口或页面截图复核。

## 10. 发布顺序

1. 从最新 `main` 创建 `codex/ci-quality-gates` 分支。
2. 提交本设计文档和后续实施计划。
3. 以测试先行方式增加工作流结构验证，再编写 `.github/workflows/ci.yml`。
4. 在本地运行能执行的全部命令，并静态检查工作流 YAML、权限和触发边界。
5. 推送分支并创建面向 `main` 的 Pull Request。
6. 等待 GitHub 托管 Runner 完成五项真实检查；修复全部失败，不以跳过方式获得绿色状态。
7. 五项检查名称可用后启用 `main` 分支保护。
8. 确认当前 Pull Request 满足保护规则，再由用户决定是否合并。
9. 合并后确认 `main` 的 `push` 运行再次通过。

## 11. 验收标准

- Pull Request 创建或更新时出现且运行五项固定检查。
- 五项检查可并行执行，任何失败都会使 Pull Request 不可合并。
- Go 全量测试、竞态检测和五个服务程序编译通过。
- Web 单元测试、TypeScript/Vite 构建和 5 项 Playwright 流程通过。
- 代理安装、恢复、现有身份修复、双架构打包和清单校验通过。
- Compose 配置解析和云令应用镜像构建通过。
- Playwright 失败时能取得 7 天内有效的诊断产物；成功运行不产生这些产物。
- 工作流权限仅为 `contents: read`，不存在 Secrets 引用、生产地址调用或部署步骤。
- `main` 规则要求 Pull Request、最新分支和五项必需检查，且禁止直接推送、强推和删除。
- 合并到 `main` 后相同检查再次通过。

## 12. 回退方案

CI 不触碰生产环境，因此失败不会影响现有云令服务。工作流自身出现问题时优先在功能分支修复。若错误的必需检查名称导致所有 Pull Request 永久等待，仓库所有者可临时移除对应必需检查、通过新的修复 Pull Request 恢复工作流，再重新启用完整规则。

只有 GitHub Actions 平台级故障且确实阻断紧急修复时，才允许临时调整保护规则。不得用直接修改生产服务器代码替代仓库修复流程。所有临时调整完成后必须恢复本设计规定的保护项，并验证 `main` 上的新运行结果。

## 13. 后续阶段

本阶段稳定后，再独立设计以下能力：

- 版本化构建产物与人工批准的生产发布。
- 生产发布前备份、迁移、健康检查和自动回滚。
- 已接入代理的版本盘点、灰度升级、自动升级和回滚。
- 团队扩展后的代码所有者和至少一人审核规则。
