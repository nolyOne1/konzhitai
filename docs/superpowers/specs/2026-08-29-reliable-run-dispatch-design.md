# 云令可靠任务派发设计

## 1. 背景与问题

生产验收已经证明以下链路工作正常：脚本发布到中央对象存储、脚本版本同步到京东云执行节点、资源与运行环境筛选、资源租约创建，以及运行实例写入 `assigned` 状态。

当前缺口位于“已分配”之后：独立调度器只把分配结果和执行令牌写入 PostgreSQL，没有组件将该记录转换成 `agentprotocol.ExecutionCommand` 并通过 API 进程持有的代理 WebSocket 连接下发。因此运行实例会永久停在 `assigned`。

## 2. 目标与非目标

### 2.1 目标

- 将 `assigned` 运行实例可靠地派发给对应在线代理。
- API 或 WebSocket 短暂故障后自动恢复，不要求人工重建运行实例。
- 使用同一个运行 ID 和执行令牌进行至少一次投递，并保证代理不会因重复投递启动第二个进程。
- 下发确定的脚本版本、入口路径、运行环境、参数、敏感参数、资源限制和超时。
- 保留现有队列、资源评分、日志、状态事件和取消接口。
- 让生产库中已经处于 `assigned` 的运行实例在部署后自动继续执行。

### 2.2 非目标

- 不把 WebSocket 所有权迁移到调度器。
- 不引入新的消息队列或新的长期服务。
- 不改变任务排队和服务器评分算法。
- 不承诺跨执行节点的严格“恰好一次”语义；系统提供执行令牌约束下的幂等至少一次派发。

## 3. 方案比较与决策

### 3.1 采用：API 持久化派发器

API 已经持有代理连接中心。新增派发器从 PostgreSQL 领取可派发记录、构造执行命令并通过现有连接中心发送。数据库记录派发尝试，短暂失败按固定间隔重试。

优点是复用现有数据库、WebSocket 和执行协议，不增加服务；API 重启后可从数据库继续。缺点是 API 增加一个后台职责，但该职责边界可以封装在独立包中。

### 3.2 未采用：Redis Stream

调度器将分配事件写入 Redis Stream，API 作为消费者下发。该方案延迟低、适合多实例，但需要消费组、确认、重放和数据库一致性处理；当前单 API 部署没有必要引入这层复杂度。

### 3.3 未采用：调度器直接维护 WebSocket

这会让调度器同时承担资源决策、外部连接认证和代理会话，破坏现有服务边界，并与 API 当前的连接中心冲突。

## 4. 组件与职责

新增 `internal/dispatch` 包，包含三个清晰边界：

- `PostgresStore`：原子领取可派发运行、读取完整执行载荷、记录发送成功或失败。
- `Service`：构造 `agentprotocol.Assignment`，解析敏感参数，调用命令发送器，区分可重试和终止错误。
- API 后台循环：按固定间隔调用派发器；生命周期跟随 API 进程，错误写入现有中文日志。

现有组件职责保持不变：

- Scheduler 负责筛选服务器、资源租约和写入 `assigned` 与执行令牌。
- `AgentConnectionHub` 负责把命令写入指定服务器的已认证 WebSocket。
- Agent 负责校验脚本路径、启动隔离进程、上报状态与日志。
- `task.EventService` 继续作为运行状态转换的唯一入口。

## 5. 数据模型与领取协议

在 `task_runs` 增加：

- `dispatch_attempts integer NOT NULL DEFAULT 0`
- `last_dispatch_at timestamptz NULL`
- `dispatch_error text NOT NULL DEFAULT ''`

派发器每 2 秒扫描一次，每批最多领取 20 条。可领取条件为：

- 状态仍为 `assigned`；
- `last_dispatch_at` 为空，或距离当前时间至少 10 秒。

领取在单个事务中完成：使用 `FOR UPDATE SKIP LOCKED` 选择记录，随后递增 `dispatch_attempts`、更新 `last_dispatch_at` 并清空旧错误。这样未来即使运行多个 API 实例，同一重试窗口内也只有一个实例领取记录。

发送失败时：

- 代理未连接、WebSocket 写失败等瞬时错误写入经过长度限制的 `dispatch_error`，运行保持 `assigned`，下个重试窗口继续。
- 缺失执行令牌、脚本版本/入口损坏、敏感参数无法解析等确定性错误通过运行事件服务把实例置为 `failed`，避免无限循环。

发送成功后运行仍保持 `assigned`，直到代理的 `started` 事件将其转换为 `running`。如果确认事件丢失，10 秒后使用相同执行令牌重复下发。

## 6. 执行载荷

派发查询一次性读取：

- 运行 ID、执行令牌和目标服务器 ID；
- 脚本 ID、确定版本 ID、入口文件和运行环境；
- 参数快照与任务敏感参数绑定；
- CPU、内存、磁盘和超时。

脚本入口路径按代理现有缓存布局生成：

`/var/lib/yunling-agent/script-cache/scripts/<脚本ID>/<版本ID>/<入口文件>`

进程环境包含：

- `YUNLING_RUN_ID`
- `YUNLING_SCRIPT_VERSION_ID`
- `YUNLING_PARAMETERS_JSON`：运行实例的普通参数快照。
- `YUNLING_SECRETS_JSON`：按任务绑定名称组织、仅在派发时解密的敏感参数。

两个 JSON 值均使用 UTF-8，支持全中文参数名。敏感值不写入 API 日志、数据库派发错误或验收输出；现有日志脱敏器继续按任务绑定解析敏感值并过滤脚本输出。

首期 `Arguments` 保持空数组，脚本统一从上述环境变量读取参数，避免把中文键强行转换成不稳定的命令行选项。

## 7. 幂等与恢复

中央端使用调度器生成并持久化的执行令牌；所有重试必须复用该令牌，禁止重新生成。

代理端调整启动规则：

- 同一运行 ID 正在执行且令牌相同：视为重复派发，忽略，不上报失败，不启动第二个进程。
- 同一运行 ID 正在执行但令牌不同：拒绝并上报执行令牌不匹配。
- 首次接收：按现有流程启动并立即上报 `started`。

API 重启后重新扫描数据库；代理断线后，记录保持 `assigned` 并在连接恢复后继续重试。服务器被判离线时，现有 Reconciler 会把无法确认的实例转为 `unknown`，派发器不再领取。

## 8. 安全与可观测性

- 派发错误只记录错误分类和非敏感上下文，不序列化完整命令。
- 敏感参数只在 API 内存中短暂解密，经已认证 TLS WebSocket 发送。
- 不将敏感参数加入命令行、systemd 单元名称或中央审计详情。
- `GET /api/runs/{id}` 无需新增敏感字段；控制台继续只显示运行状态、节点、退出码与结果摘要。
- API 日志记录运行 ID、服务器 ID、尝试次数和成功/失败类别，便于运维定位。

## 9. 测试策略

### 9.1 单元测试

- 领取查询只返回到期的 `assigned` 记录，并递增派发次数。
- 完整载荷正确生成脚本路径、资源限制、超时和普通参数 JSON。
- 代理未连接时记录瞬时错误，状态保持 `assigned`。
- 发送成功后不提前改为 `running`。
- 同令牌重复命令不会启动第二个进程；不同令牌仍被拒绝。

### 9.2 集成测试

- PostgreSQL 事务并发领取同一运行时只有一个成功。
- 代理上报 `started`、日志和 `completed` 后，运行依次进入 `running`、`succeeded`，退出码为 0。
- 敏感参数解析失败形成终止状态，错误消息不包含敏感值。

### 9.3 生产验收

- 先更新京东云代理的同令牌幂等能力，再重建并滚动更新 API 镜像；其余六个控制面服务保持运行。
- 数据迁移完成后，现有 `assigned` 验收实例自动被领取，不创建第二个运行实例。
- 京东云执行日志必须包含“云令真实节点验收”、实际主机名、时间、CPU、可用内存和根分区可用空间。
- 最终状态必须为 `succeeded`，退出码必须为 0，执行服务器 ID 必须为 `6f445eb6-e388-4ebf-a67d-33834c816893`。

## 10. 部署与回退

部署顺序：备份数据库、构建新 API 与代理、先替换并重启兼容代理、执行向前兼容迁移、滚动更新 API、观察现有实例终态。代理更新时派发器尚未上线，现有 `assigned` 实例不会被启动；新增列均有默认值，旧 API 在短暂并存期间可以继续工作。

如果派发器异常，先回退 API 镜像；新增代理向后兼容旧 API，可以保留。新增列保留不会影响旧版本。运行实例仍停留在 `assigned`，资源租约与执行令牌不丢失，修复后可以继续派发。只有确认代理从未启动时才允许人工取消或重建运行实例。
