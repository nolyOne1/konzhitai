# 代理升级状态权限故障与首次迁移

## 故障范围

0.2.0 / 0.2.1 的 root 升级 helper 原子替换 `spec.json` 时会把文件写为 root 所有、0600。以 `yunling-agent` 运行的新代理不能读取该文件，无法确认重连；超时回滚又会把 `runtime.json` 写为 root 所有、0600，导致旧代理启动时同样报 permission denied 并反复重启。

本次修复以状态文件的**父目录 UID/GID**为身份依据，先在同目录创建随机临时文件，写入、设置 0600 和正确属主、同步并关闭，再原子替换。不能继承已损坏的旧 JSON 属主，也不能通过放宽到 0644 / 0777 来规避问题。root 与普通代理账号均须遵守同一写入规则。

安装脚本将升级根目录建立为 `yunling-agent:yunling-runner 2750`，命令目录由代理建立；文件本身仍为 owner-only。若目录本身属主不正确，须先人工核实安装布局，不能对整个目录递归 chown/chmod。

## 已失败节点的应急恢复

操作前需获得节点恢复授权，确认是在执行节点而非控制端操作。禁止打印凭据文件或环境文件。

1. 保留 journal 日志，核实错误确为升级 JSON 读取失败。停止崩溃循环中的 `yunling-agent.service`；不要在未知替换阶段直接杀掉独立升级 helper。
2. 读取磁盘二进制的 `version`、本次 helper 的状态以及两个确定路径的 JSON。只有确认 **已回到升级前版本、helper 已结束、spec.phase 为 rolled_back、runtime.stage 为 failed 且 error_code 为 apply_rolled_back** 后，才按以下方向恢复。其余阶段需单独诊断。
3. 在 root 私有的新备份目录中，以保留原属性的方式备份这两个普通、非符号链接 JSON。定点恢复为代理账号所有、0600；不改 JSON 内容，不删除运行状态、备份、身份文件或已下载制品。
4. 以真实代理账号验证文件可读、状态根目录可写，再启动代理。核对持续 active、日志无新增权限错误、相同节点 ID 的心跳在线、版本仍为升级前版本。
5. 刷新控制台，确认原计划收到失败上报并记录已回滚。检查节点是否仍在排空；应按控制台正常流程处理，不直接改数据库状态。恢复代理连接不等于恢复调度可用性。

保留 `failed/apply_rolled_back` 可让旧代理在收到**同一 command_id**时重放失败结果而不是再次安装。不要新建、重试或取消计划以生成新命令来尝试消除页面上的安装中状态。

## 0.2.0 / 0.2.1 到修复版的首次迁移

**不能直接点击自动升级并假定新版本已修好执行链路。** systemd 升级单元启动的是当前安装的 `yunling-agent apply-upgrade`。运行中的旧 Apply 进程不会因磁盘二进制被替换而变成新程序，仍可能写出不可读的 root-owned 状态。手动修好前一次 JSON 也不能保护下一次新命令。

修复版发布候选版本为 0.2.2；只有 CI 和制品校验通过后才可进入部署。首次迁移须安排独立的受控人工引导安装：

- 确认旧计划已妥善结束，没有进行中的升级 helper，待执行节点排空。
- 核对制品版本、来源提交和 SHA-256；备份现有二进制、受管 systemd/polkit 文件及状态，保留节点身份。
- 使用发布包安装脚本中**保留已有凭据和节点身份**的恢复安装路径；不重新注册节点，不粘贴或覆盖密钥。
- 核对版本、原节点 ID、服务状态和持续心跳，再做成功退出码、非零退出码、取消和超时验收。
- 首次迁移完成后，才能用已修复的 helper 验证后续自动升级和自动回滚。该验证必须使用受控测试节点及已校验的独立版本，不能把人工安装成功当作自升级验收通过。

## 回归测试

常规 `go test ./internal/agentupdate ./internal/agent ./cmd/agent` 覆盖状态机和原子文件更新。

Linux 跨用户用例需真实 root 父进程模拟 helper，并用降低到普通 UID/GID 的子进程读取及确认重连。CI 的“代理安装与打包”任务编译测试程序后通过 `sudo -n` 运行 `TestStateOwnershipRoot*`；设置 `YUNLING_TEST_REQUIRE_ROOT=1` 防止缺少权限时跳过而误报通过。普通开发机上的跳过不构成跨用户验收。
